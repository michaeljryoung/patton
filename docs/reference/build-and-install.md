# Build, install and release notes

Read before building, packaging or installing Patton, when a build or release step fails, or before trusting an exit code or a grep of the packaged asar. Moved word for word from CLAUDE.md's Gotchas (S46 slimming, 2026-11-08).

- **Forge exit codes are not proof of a build** (S40; Forge 8 in S45). Under Forge 7 on Node 26, `extract-zip` 2.0.1 drained the event loop: Forge exited 0, `out/` stayed empty and the postPackage hook never ran. Forge 8 (@electron/packager 20.3, no extract-zip) packages on Node 26, but the habit stays: build through `scripts/forge-package.sh` and prove it by `ls -l` of the asar (`out/…` for a no-install build, `/Applications/Patton.app/Contents/Resources/app.asar` for an install) being newer than the commit. The post-commit hook writes its output to `.git/post-commit-build.log`. Local `npm run make` needs Node 22–24: the DMG maker's `macos-alias` (nan 2.30) does not compile on Node 26, so install and make with `PATH=/usr/local/bin:$PATH` (Node 24) or CI's Node 22.
- **GitHub 504s on Electron's release files stop CI and local builds alike** (S46, 8 Nov 09:14–09:20). `@electron/get` fetches `SHASUMS256.txt` from github.com even with the zip cached, so `Build DMG` failed before any tag (then `gh run rerun --failed` is safe; never re-run a release that already made its tag) and a local build needs a temporary `electronZipDir: '<~/Library/Caches/electron/<hash>>'` in `packagerConfig`, reverted right after (S46 installed main that way: "1.19.0+6"). Never commit it.
- **`npm run package` can be blocked by a prod-dependency CVE, not a code error** (S29). The script is `npm audit --omit=dev --audit-level=high && electron-forge package` — one high-severity *production* advisory fails the gate before the build runs (S29: `fast-uri`). Diagnose with `npm audit --omit=dev --audit-level=high`; fix transitive vulns with a `package.json` `overrides` pin, not `audit fix --force`. Dev-only vulns don't count against this gate.
- **macOS does NOT hot-swap a replaced `.app` bundle.** After `npm run package` reinstalls to `/Applications/Patton.app`, the running Patton process is still the OLD binary. ⌘Q + relaunch required to pick up new code. Detection recipe: `ls -lt /Applications/Patton.app/Contents/Resources/app.asar` (asar mtime) vs `ps -o lstart= -p $(pgrep -f Patton.app | head -1)` (process start). If process start < asar mtime, the running build is stale. S26 (2026-04-27 evening) hit this exactly. Second confirmation channel: grep `main.log` for the post-fix log signature.
- **Packaged asar minifies identifier names but preserves literal values.** Verifying a shipped change: don't grep for original variable names (`event.detail !== 2` minifies to `a.detail!==2`). Grep for literal string constants (`'Reset Renderer'`, regex source strings) — those survive minification. To look inside the asar, extract all of it into a scratch folder (`npx asar extract <asar> <scratch dir>`) and grep there; don't use `npx asar extract-file`: it writes the file's basename into the current directory, so run from the repo root, extracting `node_modules/<pkg>/package.json` or the asar's own `package.json` overwrites Patton's `package.json` (S43: it did, and the post-commit build that was reading it failed; S45 and S57: again, from a worktree root).
- **A second Patton shares the real one's userData unless its productName differs** (S45). There is no single-instance lock, so a build launched from `out/` would read and write Michael's settings, sessions, board layout and `main.log`. To launch an untried build safely: set `"productName": "Patton Test"` in `package.json` for that one build only (`git checkout package.json` after), run `out/Patton-darwin-arm64/Patton.app/Contents/MacOS/Patton` directly, read `~/Library/Application Support/Patton Test/logs/main.log`, `pkill -9 -f` on the `out/` path, and move that folder to the Trash (a guard blocks `rm -rf` there). It may leave a "Patton Test Safe Storage" keychain item. Opening a window is on the ask-first list. (moved word for word from CLAUDE.md's Gotchas, S49 slimming, 2026-11-12)
- **Never run the Patton binary to read its version, not even with `--version`** (S56, 2026-11-20). `/Applications/Patton.app/Contents/MacOS/Patton --version` starts a full second Patton (Electron ignores the flag, and there is no single-instance lock): at 11:35:20 it ran on Michael's userData, then died of `write EPIPE` when `head -1` closed its stdout, and he saw "Patton fatal error". His running Patton was untouched and its 30 s autosave rewrote `config.json` at 11:35:31 and 11:36:01. Read the version from the bundle instead: `defaults read /Applications/Patton.app/Contents/Info.plist CFBundleShortVersionString`.
- **A quit Patton can leave its `chrome_crashpad_handler` running out of /Applications** (S51, 2026-11-13). An orphan (parent PID 1) from a 10 Nov launch was still alive three days later. `scripts/install-prune.cjs` asks `pgrep -lf` for anything running from the bundle, so the orphan would count as Patton running and the stale files would only be listed, not removed. Before an install, check `ps -axo pid,ppid,comm | grep Patton.app` and stop an orphaned handler. Do not test with `pgrep -f /Applications/Patton.app` inside a shell command: it matches the shell running it.
- **A package build in a worktree can leave `index.html` rewritten** (S53, 2026-11-14, cause not traced). After `PATTON_NO_INSTALL=1 npm run package` in `.worktrees/tabs-fill` at 09:19, `git status` showed ` M index.html`: the dev `<script src="/src/renderer/index.ts">` tag was replaced by the built `./assets/index-*.js` and `.css` tags. The fix builder reported that its next package build failed with that file in place and passed once the file was set aside. Check `git status` after a build, and put `index.html` back to its committed state before building again or committing (the dcg hook blocks `git checkout -- <file>`, so set it aside with a tagged `git stash push -m <tag> -- index.html` and drop that entry afterwards).
- **The Dock keeps its own copy of the app icon** (S67, 2026-11-26). After v1.46.1's install the Dock still showed the previous icon, the clear portrait, while NSWorkspace already returned the new one, the face drawn by falling digits. The likely cause, an inference not isolated: `ditto` overwrites in place and leaves the `.app` folder's own mtime alone, so the bundle kept its old date and the Dock kept the old icon. Which date the Dock keys on is not isolated, since the inner folders and `electron.icns` do get new times. The install now bumps the bundle's mtime and runs `lsregister -f` on it (`refreshIcon` in `scripts/install-prune.cjs`, called from `pruneAndVerify` after the signature check, install path only; `lsregister` has a 30 s timeout, the mtime bump and the registration are separate tries so one failing does not stop the other, and it is skipped when `CI` is set because a runner has no Dock). It never restarts the Dock, because the post-commit hook installs on commits too and a restart shows on screen. If the Dock still shows the old icon, `killall Dock` refreshes it. Side effect: `scripts/patton-health.sh` (about line 58) reads the `.app` folder's mtime as "built", which now follows each install, not the build. The gate in `postPackage` has its own check, `scripts/check-install-gate.mjs`.
