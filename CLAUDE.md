# Patton

Always-passthrough terminal with a floating compose panel for drafting multi-line input.

## Tech Stack
- **Electron** (v40) with Vite + TypeScript via Electron Forge
- **xterm.js** v6 (`@xterm/xterm`) — terminal rendering (WebGL addon)
- **node-pty** — PTY spawning in main process
- **electron-store** — persistent settings + history

## Architecture

```
src/
├── main/           # Electron main process (PTY, IPC, menus, settings store)
├── preload/        # contextBridge API (type-safe IPC bridge)
├── renderer/       # UI components, services, styles
│   ├── components/ # Tab, Terminal, Compose Panel, Settings, Command Palette, etc.
│   ├── services/   # Tab manager, history, keybindings
│   └── styles/     # CSS with design tokens + auto dark/light mode
├── shared/         # IPC channel constants + shared TypeScript types
└── resources/      # Shell integration scripts (zsh, bash)
```

## Commands
- `npm start` — dev mode with hot reload
- `npm run package` — build distributable
- `npm run make` — create DMG installer
- `npm run lint` — ESLint
- `npm run release [-- patch|minor|major]` — manual release (CI handles this automatically)

## Verifiers

```bash
npm run lint && npm run package
```

## Key Conventions
- All colors use CSS variables (`:root` + `@media prefers-color-scheme`)
- All interactive elements have ARIA attributes
- Resize observers are debounced (100ms)
- PTY data is write-coalesced (4ms buffer)
- electron-store needs CJS/ESM interop: `(mod.default || mod)`
- Entry files must match package.json `main` field naming (main.ts → main.js, preload.ts → preload.js)

## Mission Synthesis
Patton is a macOS Electron terminal built around two defining choices: always-passthrough xterm.js input (no modal "edit vs. send" distinction) and a floating compose panel for drafting multi-line commands without fighting the PTY. It exists because the CLI tools Michael actually uses — Claude Code in particular — expose gaps in stock terminals (missing OSC 10/11 color responses, no COLORFGBG, no contrast safety net, no attention indicator when a background tab needs input) that Patton closes deliberately, rather than copying VS Code's visible surface without its safety nets.

The app is feature-complete and distributed (DMG + Homebrew tap, self-signed, CI auto-versioned); momentum alternates between defensive hardening and incremental ergonomics. S20–22 (2026-04-18) shipped renderer-crash resilience, store-encryption rewrite, accessibility, file logger, confirm-before-quit, and the tab "awaiting input" dot. S23–24 (2026-04-20/24) ruled out a Patton cause for `/mcp` Enter hang and shipped defensive render hardening (atlas flush on theme swap, Reset Renderer command, GPU breadcrumbs) + unified double-click links + VS Code resolution. S25 (2026-04-27) diagnosed the garbled-glyph recurrence as WebGL atlas eviction and shipped Phase 1: periodic `clearTextureAtlas()` every 10 min, atlas flush on `clear`, ⌘⇧K hotkey, snapshot diagnostics (commit `89404e4`). S26 same evening confirmed the running binary at the time was pre-S25 (asar mtime AFTER process start), hot-swap gotcha bit a third time. S27 (this session, 2026-05-07) is the inflection: user reported recurrence ~Apr 30 ON the S25 binary, triggered by Cmd+Tab to another app. That disconfirmed the saturation-only diagnosis and pointed at GPU state corruption when Patton is backgrounded. Three layered defenses shipped in one pass: `backgroundThrottling: false` (prevents Chromium from suspending the renderer in background, which appears to be when the WebGL atlas state is silently invalidated), `visibilitychange` + `window.focus` handlers that flush the atlas on resume (catches the user's reported trigger directly), and an auto-reload-on-flush-error path for the case where flush alone can't recover. Plus a long-standing validation gap closed: renderer `[RENDER]` console calls now bridge to `main.log` via IPC (S26's "is the periodic timer firing?" question was unanswerable until now because renderer console wasn't teed). Periodic interval shortened 10→2 min; `document.hidden` notification check replaced with `document.hasFocus()` since `backgroundThrottling: false` pins visibilityState to 'visible'. Build clean, asar verified.

Next arc: user relaunches Patton to load the S27 fix and validates. Hypothesis ranking: backgroundThrottling pin is the load-bearing fix; visibility/focus flush is the recovery fallback; auto-reload is the last-resort safety net. If recurrence persists across all three with `[RENDER] resume atlas flush` lines confirmed in `main.log`, the cause is below xterm's WebGL addon (Chromium ANGLE/Metal layer or GPU driver) and Phase 2 — Canvas renderer fallback via `@xterm/addon-canvas` — becomes the right escalation. Three guiding lessons now thread through Gotchas: (1) "copy the config, skip the safety net" — `minimumContrastRatio`, `onContextLoss`, `safeStorage`, atlas-flush on theme change, `code` CLI fallback, **`backgroundThrottling: false` for GPU-heavy renderers** — install the enforcement, not just the defaults; (2) ranking hypotheses by *what's defensively easy to fix* over *what evidence supports* can chase the wrong root cause for a full round (S24→S25 atlas-eviction story; S25→S27 saturation-only story is the second instance — both took user-reported recurrence on the "fixed" binary to disconfirm); (3) "fix shipped" ≠ "fix loaded" — before assuming a recent fix failed, compare process start time to asar mtime (S26); and now (4) **observability gaps invalidate validation** — for ~10 days post-S25 we couldn't tell whether the periodic flush was firing because renderer console wasn't teed to disk; that lacuna is what made S26's "fix loaded?" question take a forensic recipe to answer.

## Decisions
- **2026-05-07 (S27) — `backgroundThrottling: false` is the right root-cause fix, not a workaround.** The user's reported trigger (Cmd+Tab away, come back) maps directly to Chromium's renderer-throttling behaviour on app background. With throttling enabled (default), the renderer's timers slow and parts of the GPU pipeline can degrade — atlas state ends up stale on resume. Disabling throttling keeps the renderer fully alive in background. Trade-off: slightly higher background CPU/battery for a terminal that's mostly idle anyway. Acceptable. Considered: leaving throttling on and relying solely on the visibility-flush handler — rejected because that catches the corruption AFTER it happens; the throttling pin prevents it.
- **2026-05-07 (S27) — Both `visibilitychange` and `window.focus` listeners.** macOS doesn't fire both consistently for every focus-change shape (Cmd+Tab vs click-on-window vs Mission Control). Listening to both is cheap (clearTextureAtlas() is a no-op when nothing's wrong) and covers all triggers. 1s throttle prevents thrashing on rapid Cmd+Tab spam. Considered: just `window.focus` — rejected because Chromium fires `visibilitychange` in some macOS sleep/wake paths where `focus` doesn't.
- **2026-05-07 (S27) — Auto-reload on flush error, not just log-and-continue.** S25's flush path swallowed errors with a warn; in practice, if `clearTextureAtlas()` throws, the GL context is wedged and a flush won't fix anything. Disposing+reloading the addon mirrors the user-triggered Reset Renderer recovery, which we know works. The reload is silent (no snapshot, no UI nag) because background paths shouldn't punish the user for self-healing.
- **2026-05-07 (S27) — Renderer log forwarding via IPC, not by replacing renderer console globals.** Considered monkey-patching `console.info` etc. in the renderer (mirroring main's logger pattern). Rejected: would break DevTools console-formatting plugins, complicate test setup, and obscure where logs originate. Explicit `rlog()` at the call sites is surgical — every `[RENDER]` line in `terminal-view.ts` was already a deliberate log; the cost of switching them to `rlog` is the same as keeping them on `console`.
- **2026-05-07 (S27) — `document.hasFocus()` not `document.hidden` for notification gating.** With `backgroundThrottling: false`, the Page Visibility API reports 'visible' even when the app is occluded, so `document.hidden` becomes useless as a "is the user looking at me?" signal. `document.hasFocus()` is the actual signal we want and is unaffected by the throttling pin. Surfaced as a known pitfall in Gotchas — anyone touching the notification path needs to know about this.
- **2026-05-07 (S27) — Periodic flush interval 10 → 2 min, not 5 or 1.** The visibility/focus handlers should catch the user's actual trigger directly. The periodic flush is now a safety net for non-focus-change atlas saturation (gradual pressure under unusually long output bursts). 2 min is aggressive enough to limit dwell time in any wedged state but cheap enough that the log volume stays manageable (≤30/h/pane, ≤150 entries/h with 5 panes — well within 5MB rotation). 1 min would log too much; 5 min reverts to roughly S25's behaviour.
- **2026-05-07 (S27) — Single bundled commit, not split across defenses.** The fixes are coupled: backgroundThrottling forces the document.hidden → hasFocus migration, the visibility handler depends on the new rlog helper for visibility-flush observability, the IPC channel is needed by the renderer logger. Splitting would create commits that don't individually pass real-use validation. Bundled is the right granularity here.
- **2026-04-27 (S26) — Recurrence on pre-S25 binary is NOT a Phase 2 escalation trigger.** Phase 2 (Canvas renderer fallback) was scoped to fire if recurrence happens *inside the 10-min flush window* — which requires the periodic flush to actually be running. A recurrence on the pre-fix binary is just the original bug doing what it always did; nothing about today's screenshot disconfirms S25's diagnosis or fix. Validation clock restarts at relaunch.
- **2026-04-27 (S26) — Diagnostic-only checkpoint, no Patton code commit.** S26's deliverable is the CLAUDE.md update (strengthened Gotcha + Session Log). The recommendation to ⌘Q + relaunch isn't a code change. Considered: forcing ⌘Q from a script — rejected, the user owns when terminal sessions die. Push of `89404e4` to GitHub remains gated on user's choice (S25 decision unchanged).

## Gotchas
- **`backgroundThrottling: false` in `webPreferences` is load-bearing** for the WebGL atlas-corruption defence (S27, 2026-05-07). With Chromium's default (true), the renderer is suspended/throttled when Patton goes background → on resume the WebGL texture state is silently stale or corrupted → user sees garbled glyphs until window-resize forces a reflow. Removing this setting will reintroduce the bug. Side effects: visibilityState reports 'visible' even when occluded (any "is app in background?" check must use `document.hasFocus()` not `document.hidden`); minor extra background CPU. The visibility-flush handler in `terminal-view.ts` is the recovery fallback — both layers exist deliberately.
- **`document.hidden` is unreliable in Patton** (S27). Because `backgroundThrottling: false` pins the Page Visibility API to 'visible' even when occluded, `document.hidden` is approximately always false in production. Use `document.hasFocus()` for "is the user looking at Patton?" gating. Already replaced in `app.ts:33` for the notification path; if you find another `document.hidden` callsite, it likely needs the same fix.
- **Renderer `console.*` calls don't reach `main.log` unless they go through `rlog()`** (S27). `src/main/logger.ts` only tees the main-process console. Any new `[RENDER]` or other diagnostic line you want in the file log MUST use `rlog()` from `src/renderer/services/renderer-logger.ts` — `console.info` alone reaches DevTools only and is invisible to packaged-app launches. This is exactly the gap that made S25's "is the periodic timer firing?" question unanswerable for ~10 days. `rlog()` keeps the DevTools console output too, so it's a strict superset of `console.*` for diagnostic purposes.
- **`[RENDERER]` prefix in `main.log` distinguishes renderer-bridged lines from native main-process lines** (S27). Lines starting `[RENDERER]` came through the IPC bridge from a renderer; everything else is native main-process. Useful when grepping — e.g. `grep '\[RENDERER\] \[RENDER\] resume atlas flush' main.log` finds visibility-triggered flushes specifically, vs `grep '\[RENDER\] snapshot saved'` (no `[RENDERER]` prefix) which is the main-process snapshot writer.
- **xterm.js WebGL atlas eviction is one of (at least) two distinct "garbled glyphs" triggers** — saturation-driven (S25 diagnosis: long Claude Code sessions emit many glyph variants, fixed-size atlas LRU-evicts slots, buffer cells aren't repointed) AND focus/refocus-driven (S27 diagnosis: Chromium suspends renderer in background, GPU state silently corrupts). Symptom signature is identical from the user side; only the trigger differs. Periodic `clearTextureAtlas()` (S25) addresses saturation, `backgroundThrottling: false` + visibility/focus flush (S27) addresses the focus path. Both are needed; don't remove either thinking the other handles all cases.
- **xterm.js WebGL atlas eviction is the recurring "garbled glyphs" trigger** (S25 root-cause). Long sessions with diverse glyph variants (coloured bullets, box-drawing, bold/italic/dim, many fg×bg combos) saturate the fixed-size atlas; LRU evictions reassign slots without repointing buffer cells, so historical scrollback shows wrong characters while recent output renders fine. Recovery as of S25: ⌘⇧K (Reset Renderer) or wait up to 10 min for the next periodic `clearTextureAtlas()`. Verify the periodic flush is firing via `[RENDER] periodic atlas flush` lines in `main.log`. If recurrence happens INSIDE the 10-min window, atlas saturation is faster than the timer — escalate to Phase 2 Canvas renderer.
- **`clearTextureAtlas()` is on Terminal, not WebglAddon** (xterm 6 typings — `node_modules/@xterm/xterm/typings/xterm.d.ts`). Public API; cheap; rebuilds atlas lazily on next render. **No addon disposal needed.** S24's `setCustomTheme()` path disposes+reloads the WebglAddon (more expensive, ~1 frame flicker) — keep that pattern only for when colors actually change. For periodic / heuristic flushes, plain `clearTextureAtlas()` is the right tool.
- **`app.getVersion()` in `main.log` returns `1.0.0` even after CI-versioned releases.** The release script tags git but doesn't bump `package.json` (per repo convention — git tags are source of truth). The `Patton main process started (vX.Y.Z, ...)` startup line is therefore meaningless for diagnosing "is the running build current?". Use the asar mtime instead: `ls -lt /Applications/Patton.app/Contents/Resources/app.asar` — that timestamp matches when `npm run package` last ran.
- **S24→S25 lesson on hypothesis ranking under unreproducible bugs.** When the user can't reproduce a bug, ranking hypotheses by "what's defensively easy to fix" rather than "what evidence supports" can chase the wrong root cause for an entire round. S24 led with theme-swap and context-loss because they were code-tractable; the actual cause was gradual atlas saturation, which the existing evidence (one-off, no crash, no logged context loss) was already pointing toward. Rule going forward: in unreproducible-bug territory, rank hypotheses by what *evidence supports*, not by *what's easy to mitigate*. Defensive fixes for the wrong cause buy nothing but session burn — and worse, they create the false belief that the bug is fixed.
- **`setCustomTheme()` is called BEFORE `mount()` on new tabs that inherit the current theme** (`tab-manager.ts:153-155`). Any WebGL-aware code in setCustomTheme must guard `if (this.webglAddon)` — otherwise it'll try to dispose/reload an addon that doesn't exist yet. The guard is in place; don't remove it when refactoring. Post-mount theme changes hit the real flush path; pre-mount just sets the theme option for the upcoming `loadWebgl()` call.
- **Silent ENOENT in `main.log` for days before detection.** Before session 24, `spawn code ENOENT` had been logging 20+ times across 4 days because `code` wasn't on PATH. Nothing surfaced it — file logger writes warnings that no one reads unless something else prompts a look. Worth a periodic log-scan in `scripts/patton-health.sh` or a session-start greeting that counts recent warnings; deferred for now.
- **xterm.js `ILink.activate(event, text)` receives the native `MouseEvent` — but whether `event.detail === 2` reliably fires for double-click is unverified as of session 24.** If double-click appears to do nothing, the fallback is a native `dblclick` listener on `terminal.element` that hit-tests against the active link range. Don't assume the minimal-change path works without real-world verification.
- **WebGL glyph atlas is keyed by color and can go stale on theme swap.** xterm.js's WebGL renderer caches glyphs keyed by `(char, bold, italic, fg_color, bg_color, ...)`. `terminal.options.theme = newTheme` mutates resolution but does NOT invalidate the cache — the next frame can pull glyphs rendered under the OLD palette. Fix: dispose+reload the WebglAddon on every theme change. Pattern matches the `minimumContrastRatio` / `onContextLoss` story: copying VS Code's config without its safety nets leaves subtle breakage.
- **Packaged asar minifies identifier names but preserves literal values.** Verifying a shipped change: don't grep for original variable names (`event.detail !== 2` minifies to `a.detail!==2`). Grep for literal values + minified operator forms, or for unique string constants that survive minification (e.g. `'Reset Renderer'` palette label, regex source strings like `\\[([^\\]\\n]+)\\]`).
- **Enter "not working" in a Claude Code subscreen (e.g. `/mcp` auth wait) is not automatically a Patton bug.** Patton's Enter handling is one code path: `attachCustomKeyEventHandler` returns `true` for plain Enter, xterm.js sends `\r`. If main-prompt Enter works in the same session, keystrokes ARE reaching the PTY — the subscreen's own stdin reader is the suspect. Discriminator before blaming Patton: press Ctrl+C / any letter key during the stuck prompt. If those also fail → Patton focus or keystroke-delivery bug (instrument `terminal-view.ts` with a file-logged `onKey` tracer). If only Enter fails → app-side handler issue, not ours.
- **xterm.js v6 registers no kitty keyboard / CSI-u handler by default.** Apps that send `\x1b[>1u` (push progressive-enhancement flags) get silently ignored — the terminal keeps sending `\r` for Enter, not `\x1b[13u`. Only matters if a TUI app hard-requires kitty-format Enter; Patton's current consumers (Claude Code, fish, neovim) work fine without it, so leaving unregistered is deliberate.
- **OSC 133 `'prompt'` is not "awaiting input".** It fires on every prompt redraw — shell startup, session restore, SIGWINCH, `clear`, async-prompt theme refreshes (Starship, Powerlevel10k). Using it as the SET signal for an attention indicator means every inactive tab lights up ~always. The right signal for "a meaningful event just happened" is the transition tracked by `pane.ts fireCommandDone()`.
- **Layering multiple `window.on('close')` handlers doesn't work for guards.** Electron runs every registered 'close' handler even if one calls `e.preventDefault()` — a guard handler registered before a destructive one can't prevent the destructive one from running. The guard must live INSIDE the destructive handler so teardown only runs when the guard passes.
- **Claude Code's "·" tab-title prefix is text INSIDE the title (OSC 2), not a chrome element.** The user visually conflates it with any indicator Patton renders near the title, especially at small sizes. Visual amplification of Patton's own indicator (size / glow / pulse) is load-bearing so the two are distinguishable at a glance.
- **Testing that the dot fires requires the signal to arrive while the tab is INACTIVE.** `raiseAwaitingInput()` gates on `!_isActive`. Running `printf '\e]9;test\a'` in the tab you're watching and then switching away can't work — the signal already fired while the tab was active. Use a delayed command (`sleep N && <signal>`) and switch tabs during the delay.
- **Packaged Electron apps launched from Dock/Finder route main-process stderr to `/dev/null`.** `console.error` / `console.warn` in the main process go nowhere visible unless the app ships its own file logger OR the user launches from a terminal (`/Applications/Patton.app/Contents/MacOS/Patton`). Without file logging, every hardening signal is invisible to the user. See `src/main/logger.ts`.
- **macOS does NOT hot-swap a replaced `.app` bundle. After `npm run package` reinstalls to `/Applications/Patton.app`, the currently running Patton process is still the OLD binary in memory.** A full ⌘Q + relaunch (not just close-window) is required to pick up the new code. **Detection recipe** — run BEFORE assuming a recent fix didn't work, BEFORE escalating, BEFORE writing more code: `ls -lt /Applications/Patton.app/Contents/Resources/app.asar` for the asar mtime, `ps -o lstart= -p <pid>` for process start time (`pgrep -f Patton.app | head -1` to find the PID). If process start is BEFORE asar mtime, the running build is stale. S26 (2026-04-27 evening) hit exactly this: a third bug recurrence looked like the S25 fix had failed; in fact the running PID had started 8 minutes before the new asar was packaged. A second confirmation channel: grep `main.log` for the post-fix log signature (e.g. `[RENDER] periodic atlas flush` for S25) — if the running build has the fix, you'll see those lines.
- `createWriteStream(..., { flags: 'a' })` does NOT create the file on construction; it creates on first write. A file-based logger that lazy-opens will never create the file on completely clean sessions where nothing logs. Eagerly write a "started" line on install.
- `window.reload()` does NOT destroy main-process PTYs. Without an explicit `ptyManager.destroyByWindow(window)` before reload, each crash-recovery reload leaks PTYs — they keep running in main, sending PTY_DATA for ids the new renderer doesn't recognize, eventually hitting `MAX_PTY_PER_WINDOW`. Crash handling without PTY cleanup makes crashes *worse*.
- `beforeunload` is fire-and-forget and does NOT fire on renderer crash. A periodic autosave (30s) is the only way to keep persisted state close to reality for crash recovery.
- wrapper `.zshenv` in ZDOTDIR mode sources user's `.zshenv` AFTER ours runs but BEFORE Patton's integration script. A compromised user `.zshenv` can redirect `PATTON_SHELL_INTEGRATION_SCRIPT` to a malicious path unless we `typeset -r`/`readonly` the captured value first.
- Electron's `safeStorage` is only available after `app.ready`. Store must be lazy-initialized (first access inside `app.on('ready', ...)` is fine; at module load would fail).
- `electron-store` doesn't expose a "try decrypt" probe — any mismatch throws. Migration has to instantiate a temp store with the legacy key, snapshot `store.store`, delete the file, then reinit with the new key.
- xterm.js WebGL addon fires `onContextLoss` at runtime (sleep/wake, display unplug, GPU driver reset). A plain `try { loadAddon }` catches sync load errors only — runtime loss will take down the whole renderer unless you subscribe to `onContextLoss` and `dispose()` the addon (falls back to DOM). Identical pattern to `minimumContrastRatio` — VS Code does it, copying only the configuration values without the safety nets is a trap.
- Dead IPC surfaces accumulate. `PTY_GET_DESCENDANTS` returned `[]` for months with no callers but was still exposed via preload — potential attack surface for future renderer code. Periodically grep for IPC handlers and confirm callers exist.
- Shell validation drift: `store.ts` had a permissive regex (`/^\/[a-zA-Z0-9/._-]+$/`) while `pty-manager.ts` enforced a tight `ALLOWED_SHELLS` Set. User could save `/usr/local/bin/fish`, see it persist, silently get the default. Always single-source security-relevant allowlists.
- `stty -echo` on the same line as `source ...` does NOT prevent echo — the terminal driver echoes characters as they arrive, before the shell executes anything. Must inject via shell startup (ZDOTDIR, --rcfile) not PTY write.
- Idle detection fires on ANY PTY data, including prompt redraws and background trickle. Duration guard is essential — byte count alone isn't enough since small periodic output accumulates.
- xterm.js treats Shift+Enter identically to Enter (`\r`) by default. Must use `attachCustomKeyEventHandler` to intercept and send a distinct escape sequence.
- xterm.js `attachCustomKeyEventHandler` fires for BOTH `keydown` AND `keypress`. Returning `false` only on `keydown` still lets `keypress` through, causing xterm to send `\r`. Must return `false` for both event types.
- CLI apps (Claude Code, etc.) use `COLORFGBG` env var to detect light vs dark terminal backgrounds. Without it, they assume dark and render light-colored text — invisible on light backgrounds. Must set at PTY spawn time; can't change env vars for running PTYs.
- CLI apps also query terminal colors at runtime via OSC 10/11 escape sequences (`\x1b]10;?\x07` and `\x1b]11;?\x07`). xterm.js doesn't respond to these by default — must hook `onData` and write back `rgb:RR/GG/BB` responses.
- `tabBar.update()` rebuilds the entire DOM (`innerHTML = ''`). Any click-triggered callback that calls `updateTabBar` will destroy elements mid-interaction (e.g., breaking `dblclick` because the first click's target is gone). Guard with early-returns for no-op state transitions.
- Light terminal ANSI colors need explicit contrast checking. xterm.js default `minimumContrastRatio` is 1 (disabled). Colors like `#a5a5a5` (brightWhite) or `#14ce14` (brightGreen) are invisible on white. VS Code uses the same palette but enables contrast enforcement — copying just the colors without the setting is a trap.
