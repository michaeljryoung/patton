# Patton

Always-passthrough terminal with a floating compose panel for drafting multi-line input.

## Tech Stack
- **Electron** (v40) with Vite + TypeScript via Electron Forge
- **xterm.js** v6 (`@xterm/xterm`) — terminal rendering (WebGL addon)
- **node-pty** — PTY spawning in main process
- **electron-store** — persistent settings + history

## Architecture

```
src/
├── main/           # Electron main process (PTY, IPC, menus, settings store)
├── preload/        # contextBridge API (type-safe IPC bridge)
├── renderer/       # UI components, services, styles
│   ├── components/ # Tab, Terminal, Compose Panel, Settings, Command Palette, etc.
│   ├── services/   # Tab manager, history, keybindings
│   └── styles/     # CSS with design tokens + auto dark/light mode
├── shared/         # IPC channel constants + shared TypeScript types
└── resources/      # Shell integration scripts (zsh, bash)
```

## Commands
- `npm start` — dev mode with hot reload
- `npm run package` — build distributable
- `npm run make` — create DMG installer
- `npm run lint` — ESLint
- `npm run release [-- patch|minor|major]` — manual release (CI handles this automatically)

## Verifiers

```bash
npm run lint && npm run package
```

## Key Conventions
- All colors use CSS variables (`:root` + `@media prefers-color-scheme`)
- All interactive elements have ARIA attributes
- Resize observers are debounced (100ms)
- PTY data is write-coalesced (4ms buffer)
- electron-store needs CJS/ESM interop: `(mod.default || mod)`
- Entry files must match package.json `main` field naming (main.ts → main.js, preload.ts → preload.js)

## Mission Synthesis
Patton is a macOS Electron terminal with always-passthrough xterm.js input and a floating compose panel for multi-line drafting. It exists to close stock-terminal gaps Claude Code exposes (OSC 10/11 colour responses, COLORFGBG, contrast safety net, background-tab attention indicator). Feature-complete and distributed (DMG + Homebrew tap, self-signed, CI auto-versioned on push to main). Its defining saga was a garbled-glyph render corruption rooted in xterm's WebGL GPU glyph atlas: S24–S28 fought it with escalating atlas-flush defences; S29 proved those were the wrong layer (flushes fired 60k+× and still didn't prevent it) and pivoted to a *structural* fix — a renderer toggle dropping xterm to its GPU-free DOM renderer, which has no atlas and so is immune. S29 shipped it as an opt-in (WebGL still default) and the glyphs stopped. **S30 closed the loop**: with DOM validated over real use it's now the default for fresh installs — a new user is structurally safe out of the box while WebGL stays one click away for its perf. Shipped as v1.6.0; the long-stale Homebrew tap was manually bumped to match (CI's auto-update stays blocked on an expired token the user chose not to refresh, so each release needs a manual tap bump). Next arc: backlog — OSC 8 hyperlinks, a dev-dep CVE pass (prod `fast-uri` patched), double-click-link validation, the S20 punch-list. Constraints: self-signed dist, ⌘Q+relaunch after packaging, expired `HOMEBREW_PAT`. Guiding lesson: when a "closed" bug returns, suspect the *layer* not the dose — and once a structural escape hatch proves out, promote it to the default rather than leaving safety opt-in.

## Gotchas
- **Claude Code v2.1.x "fullscreen rendering" breaks selection AND can re-trigger glyph corruption** (S29, 2026-06-05). Opt-in research preview (alt-screen buffer + mouse capture; the "Jump to bottom" pill is the tell). Mouse capture sends drags to Claude Code not the terminal → "can't highlight text"; the alt-screen path also re-stresses xterm's WebGL atlas. Disable via `/tui default` (full revert) or `CLAUDE_CODE_DISABLE_MOUSE=1` (keep flicker-free). Patton's answer: the renderer toggle + `macOptionClickForcesSelection`. Docs: `code.claude.com/docs/en/fullscreen`.
- **On macOS, xterm v6 ignores Shift for selection during mouse mode** (S29). `shouldForceSelection` = `isMac ? altKey && macOptionClickForcesSelection : shiftKey`. So on Mac you MUST set `macOptionClickForcesSelection: true` (now set in `terminal-view.ts`) and hold **Option** to drag-select while an app (Claude Code fullscreen, vim, tmux, htop) holds the mouse. Without it there is no selection escape hatch at all.
- **DOM renderer is the structural fix for glyph corruption — and as of S30 it's the DEFAULT** (`DEFAULTS.RENDERER='dom'`). It never loads (or disposes) the WebglAddon → xterm falls back to DOM → no GPU glyph atlas → the whole corruption class is structurally impossible. Fresh installs land here; WebGL ("GPU — fast") is a one-click opt-in (palette → "Switch to GPU Renderer", or Settings → Text Renderer). Existing users' saved choice overrides the default. Confirm DOM is active by `[RENDER] *atlas flush` lines being ABSENT in `main.log` (flush paths no-op when `!webglAddon`). Cost: marginally heavier on huge output bursts.
- **`npm run package` can be blocked by a prod-dependency CVE, not a code error** (S29). The script is `npm audit --omit=dev --audit-level=high && electron-forge package` — one high-severity *production* advisory fails the gate before the build runs (S29: `fast-uri`). Diagnose with `npm audit --omit=dev --audit-level=high`; fix transitive vulns with a `package.json` `overrides` pin, not `audit fix --force`. Dev-only vulns don't count against this gate.
- **`backgroundThrottling: false` in `webPreferences` is load-bearing** for the WebGL atlas-corruption defence (S27, 2026-05-07). With Chromium's default (true), the renderer is suspended/throttled when Patton goes background → on resume the WebGL texture state is silently stale or corrupted → user sees garbled glyphs until window-resize forces a reflow. Removing this setting will reintroduce the bug. Side effects: visibilityState reports 'visible' even when occluded (any "is app in background?" check must use `document.hasFocus()` not `document.hidden`); minor extra background CPU. The visibility-flush handler in `terminal-view.ts` is the recovery fallback — both layers exist deliberately.
- **`document.hidden` is unreliable in Patton** (S27). Because `backgroundThrottling: false` pins the Page Visibility API to 'visible' even when occluded, `document.hidden` is approximately always false in production. Use `document.hasFocus()` for "is the user looking at Patton?" gating. Already replaced in `app.ts:33` for the notification path; if you find another `document.hidden` callsite, it likely needs the same fix.
- **Renderer `console.*` calls don't reach `main.log` unless they go through `rlog()`** (S27). `src/main/logger.ts` only tees the main-process console. Any new `[RENDER]` or other diagnostic line you want in the file log MUST use `rlog()` from `src/renderer/services/renderer-logger.ts` — `console.info` alone reaches DevTools only and is invisible to packaged-app launches. This is exactly the gap that made S25's "is the periodic timer firing?" question unanswerable for ~10 days. `rlog()` keeps the DevTools console output too, so it's a strict superset of `console.*` for diagnostic purposes.
- **`[RENDERER]` prefix in `main.log` distinguishes renderer-bridged lines from native main-process lines** (S27). Lines starting `[RENDERER]` came through the IPC bridge from a renderer; everything else is native main-process. Useful when grepping — e.g. `grep '\[RENDERER\] \[RENDER\] resume atlas flush' main.log` finds visibility-triggered flushes specifically, vs `grep '\[RENDER\] snapshot saved'` (no `[RENDERER]` prefix) which is the main-process snapshot writer.
- **xterm WebGL atlas eviction = the "garbled glyphs" root cause; two triggers, now sidestepped by DOM-default** (S25/S27). Saturation-driven (long sessions emit many glyph variants → fixed-size atlas LRU-evicts slots without repointing buffer cells → wrong chars in scrollback) AND focus/refocus-driven (Chromium suspends the renderer in background → GPU state silently corrupts). Identical symptom, different trigger. Only matters on WebGL now that S30 made DOM the default; a WebGL opt-in user who hits it can rely on the S25/S27 defences (periodic + visibility/focus `clearTextureAtlas()`, `backgroundThrottling:false`, ⌘⇧K reset) or just switch to DOM. Full saga + per-defence rationale in `docs/session-archive.md`.
- **`clearTextureAtlas()` is on Terminal, not WebglAddon** (xterm 6 typings — `node_modules/@xterm/xterm/typings/xterm.d.ts`). Public API; cheap; rebuilds atlas lazily on next render. **No addon disposal needed.** S24's `setCustomTheme()` path disposes+reloads the WebglAddon (more expensive, ~1 frame flicker) — keep that pattern only for when colors actually change. For periodic / heuristic flushes, plain `clearTextureAtlas()` is the right tool.
- **`app.getVersion()` in `main.log` returns `1.0.0` even after CI-versioned releases.** The release script tags git but doesn't bump `package.json` (per repo convention — git tags are source of truth). The `Patton main process started (vX.Y.Z, ...)` startup line is therefore meaningless for diagnosing "is the running build current?". Use the asar mtime instead: `ls -lt /Applications/Patton.app/Contents/Resources/app.asar` — that timestamp matches when `npm run package` last ran.
- **`release.yml`'s Homebrew-cask step FAILS (not skips) on an expired `HOMEBREW_PAT`** (S28). The `if [ -z "$HOMEBREW_PAT" ]` guard only catches an UNSET secret; an expired-but-present token passes it, then fails at `git clone https://x-access-token:<expired>@...`. The GitHub-release step (prior, uses `${{ github.token }}`) still succeeds — so a run shows red ✗ while the release is intact. `HOMEBREW_PAT` (set 2026-03-09) was expired by S28; the brew tap stays on the last-good version until refreshed (`gh secret set HOMEBREW_PAT`). Local push + GitHub release never depend on it.
- **Homebrew tap is a separate repo; bump it by hand when CI's auto-update fails** (S30). `michaeljryoung/homebrew-patton` holds one cask file, `Casks/patton.rb` (local clone: `~/Projects/homebrew-patton`). After a release, if the `Update Homebrew cask` CI step is red (expired `HOMEBREW_PAT`), the tap freezes at the old version. Manual fix: edit `version` + `sha256` (the `url` auto-resolves from `version`), push via the gh OAuth token — no PAT needed; only CI's auto-update needs it. VERIFY the sha256 first (`curl -sL <dmg-url> | shasum -a 256`; a wrong hash silently breaks every `brew install`); it's also in the release body's `### Checksums` table. S30 did exactly this to take the tap 1.3.0→1.6.0.
- **`setCustomTheme()` is called BEFORE `mount()` on new tabs that inherit the current theme** (`tab-manager.ts:153-155`). Any WebGL-aware code in setCustomTheme must guard `if (this.webglAddon)` — otherwise it'll try to dispose/reload an addon that doesn't exist yet. The guard is in place; don't remove it when refactoring. Post-mount theme changes hit the real flush path; pre-mount just sets the theme option for the upcoming `loadWebgl()` call.
- **Garbled-glyph "atlas eviction" symptom is not always a Patton bug** (S27 reorientation, 2026-05-07). User confirmed the same character-corruption signature reproduces in **iTerm2** during the period S25/S26/S27 spent diagnosing it as a Patton/xterm.js issue. Both Patton (WebGL via ANGLE/Metal) and iTerm2 (native Metal) sit downstream of the macOS GPU + CoreText font subsystem — a system-level issue (font-cache corruption, Metal driver state, OS update) presents identically in both. Discriminator: reproduce in **Apple Terminal.app** (CoreGraphics, no Metal). Same → font/CoreText layer; only Metal-using apps → GPU layer. Triage: `sudo atsutil databases -remove` + restart resets CoreText's glyph cache. S27's defences (`backgroundThrottling: false`, visibility-flush, auto-reload) still ship as defensive value but were chasing a Patton-shape cause for a system-shape bug. Lesson reinforces #2 above: when a user can't reproduce on demand, **check whether the bug reproduces in a different terminal app** before any hypothesis about Patton internals.
- **macOS does NOT hot-swap a replaced `.app` bundle.** After `npm run package` reinstalls to `/Applications/Patton.app`, the running Patton process is still the OLD binary. ⌘Q + relaunch required to pick up new code. Detection recipe: `ls -lt /Applications/Patton.app/Contents/Resources/app.asar` (asar mtime) vs `ps -o lstart= -p $(pgrep -f Patton.app | head -1)` (process start). If process start < asar mtime, the running build is stale. S26 (2026-04-27 evening) hit this exactly. Second confirmation channel: grep `main.log` for the post-fix log signature.
- **Packaged asar minifies identifier names but preserves literal values.** Verifying a shipped change: don't grep for original variable names (`event.detail !== 2` minifies to `a.detail!==2`). Grep for literal string constants (`'Reset Renderer'`, regex source strings) — those survive minification.
- **Packaged Electron apps launched from Dock/Finder route main-process stderr to `/dev/null`.** Without a file logger, every main-process signal is invisible. See `src/main/logger.ts`. Renderer console doesn't even reach that — see the rlog gotcha above.
- **WebGL glyph atlas is keyed by color and can go stale on theme swap.** xterm's WebGL renderer caches glyphs keyed by `(char, bold, italic, fg_color, bg_color, ...)`. `terminal.options.theme = newTheme` mutates resolution but does NOT invalidate the cache — fix is dispose+reload the WebglAddon on every theme change. Same shape as the `minimumContrastRatio` / `onContextLoss` story.
- **xterm.js v6 registers no kitty/CSI-u handler by default.** Apps sending `\x1b[>1u` (push progressive-enhancement flags) get silently ignored — terminal keeps sending `\r` for Enter, not `\x1b[13u`. Patton's current consumers (Claude Code, fish, neovim) work fine without it.
- **OSC 133 `'prompt'` is not "awaiting input".** Fires on every prompt redraw — shell startup, session restore, SIGWINCH, `clear`, async-prompt refreshes (Starship, Powerlevel10k). Use `pane.ts fireCommandDone()` for the meaningful-transition signal.
- **Layering multiple `window.on('close')` handlers doesn't work for guards.** Electron runs every registered 'close' handler even if one calls `e.preventDefault()`. The guard must live INSIDE the destructive handler so teardown only runs when the guard passes.
- **xterm.js `attachCustomKeyEventHandler` fires for BOTH `keydown` AND `keypress`.** Returning `false` only on `keydown` still lets `keypress` through, causing xterm to send `\r`. Must return `false` for both event types.
