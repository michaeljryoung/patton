# Patton

Always-passthrough terminal with a floating compose panel for drafting multi-line input.

## Tech Stack
- **Electron** (v40) with Vite + TypeScript via Electron Forge
- **xterm.js** v6 (`@xterm/xterm`) — terminal rendering (WebGL addon)
- **node-pty** — PTY spawning in main process
- **electron-store** — persistent settings + history

## Architecture

```
src/
├── main/           # Electron main process (PTY, IPC, menus, settings store)
├── preload/        # contextBridge API (type-safe IPC bridge)
├── renderer/       # UI components, services, styles
│   ├── components/ # Tab, Terminal, Compose Panel, Settings, Command Palette, etc.
│   ├── services/   # Tab manager, history, keybindings
│   └── styles/     # CSS with design tokens + auto dark/light mode
├── shared/         # IPC channel constants + shared TypeScript types
└── resources/      # Shell integration scripts (zsh, bash)
```

## Commands
- `npm start` — dev mode with hot reload
- `npm run package` — build distributable
- `npm run make` — create DMG installer
- `npm run lint` — ESLint
- `npm run release [-- patch|minor|major]` — manual release (CI handles this automatically)

## Verifiers

```bash
npm run lint && npm run package
```

## Key Conventions
- All colors use CSS variables (`:root` + `@media prefers-color-scheme`)
- All interactive elements have ARIA attributes
- Resize observers are debounced (100ms)
- PTY data is write-coalesced (4ms buffer)
- electron-store needs CJS/ESM interop: `(mod.default || mod)`
- Entry files must match package.json `main` field naming (main.ts → main.js, preload.ts → preload.js)

## Mission Synthesis
Patton is a macOS Electron terminal with always-passthrough xterm.js input and a floating compose panel for multi-line drafting. It exists to close stock-terminal gaps that Claude Code in particular exposes (OSC 10/11 color responses, COLORFGBG, contrast safety net, attention indicator on background tabs) — copying VS Code's visible surface without its safety nets is the recurring failure mode being avoided.

Feature-complete and distributed (DMG + Homebrew tap, self-signed, CI auto-versioned). Recent arc: S20–22 shipped renderer-crash resilience, store encryption, accessibility, file logger, confirm-before-quit, tab "awaiting input" dot. S23–24 ruled out a Patton cause for an Enter-hang and shipped render hardening + double-click links + VS Code resolution. S25 diagnosed garbled glyphs as WebGL atlas eviction and shipped Phase 1 (periodic `clearTextureAtlas()`, ⌘⇧K hotkey, snapshot diagnostics). S26 caught the macOS asar-hot-swap gotcha for the third time. S27 (2026-05-07, this session): user reported recurrence on the S25 binary triggered by Cmd+Tab — disconfirms saturation-only. Three layered defences shipped (`backgroundThrottling: false` to stop Chromium suspending the renderer; `visibilitychange`+`window.focus` atlas-flush handlers; auto-reload on flush error) plus a renderer-log → `main.log` IPC bridge that closes the S25-era observability gap.

Next arc: validate S27 in real use. If recurrence persists with `[RENDERER] [RENDER] resume atlas flush` lines confirming the handler fired, corruption is below xterm and Phase 2 (Canvas renderer fallback) is the escalation. Constraints unchanged: self-signed distribution, ⌘Q+relaunch required after `npm run package`, allowlists single-sourced. Four guiding lessons thread through Gotchas: (1) "copy the config, skip the safety net" recurs across `minimumContrastRatio`, `safeStorage`, `backgroundThrottling`, `onContextLoss` — install the enforcement; (2) under unreproducible bugs, rank hypotheses by *evidence supports* not *easy to fix* (S24→S25→S27 took two false-direction rounds before user-reported recurrence on the "fixed" binary disconfirmed each); (3) "fix shipped" ≠ "fix loaded" (asar mtime vs PID lstart, S26); (4) observability gaps invalidate validation — the renderer-console → file gap made S25's "is the timer firing?" question unanswerable for 10 days.

## Decisions
- **2026-05-07 (S27) — `backgroundThrottling: false` is the right root-cause fix, not a workaround.** The user's reported trigger (Cmd+Tab away, come back) maps directly to Chromium's renderer-throttling behaviour on app background. With throttling enabled (default), the renderer's timers slow and parts of the GPU pipeline can degrade — atlas state ends up stale on resume. Disabling throttling keeps the renderer fully alive in background. Trade-off: slightly higher background CPU/battery for a terminal that's mostly idle anyway. Acceptable. Considered: leaving throttling on and relying solely on the visibility-flush handler — rejected because that catches the corruption AFTER it happens; the throttling pin prevents it.
- **2026-05-07 (S27) — Both `visibilitychange` and `window.focus` listeners.** macOS doesn't fire both consistently for every focus-change shape (Cmd+Tab vs click-on-window vs Mission Control). Listening to both is cheap (clearTextureAtlas() is a no-op when nothing's wrong) and covers all triggers. 1s throttle prevents thrashing on rapid Cmd+Tab spam. Considered: just `window.focus` — rejected because Chromium fires `visibilitychange` in some macOS sleep/wake paths where `focus` doesn't.
- **2026-05-07 (S27) — Auto-reload on flush error, not just log-and-continue.** S25's flush path swallowed errors with a warn; in practice, if `clearTextureAtlas()` throws, the GL context is wedged and a flush won't fix anything. Disposing+reloading the addon mirrors the user-triggered Reset Renderer recovery, which we know works. The reload is silent (no snapshot, no UI nag) because background paths shouldn't punish the user for self-healing.
- **2026-05-07 (S27) — Renderer log forwarding via IPC, not by replacing renderer console globals.** Considered monkey-patching `console.info` etc. in the renderer (mirroring main's logger pattern). Rejected: would break DevTools console-formatting plugins, complicate test setup, and obscure where logs originate. Explicit `rlog()` at the call sites is surgical — every `[RENDER]` line in `terminal-view.ts` was already a deliberate log; the cost of switching them to `rlog` is the same as keeping them on `console`.
- **2026-05-07 (S27) — `document.hasFocus()` not `document.hidden` for notification gating.** With `backgroundThrottling: false`, the Page Visibility API reports 'visible' even when the app is occluded, so `document.hidden` becomes useless as a "is the user looking at me?" signal. `document.hasFocus()` is the actual signal we want and is unaffected by the throttling pin. Surfaced as a known pitfall in Gotchas — anyone touching the notification path needs to know about this.
- **2026-05-07 (S27) — Periodic flush interval 10 → 2 min, not 5 or 1.** The visibility/focus handlers should catch the user's actual trigger directly. The periodic flush is now a safety net for non-focus-change atlas saturation (gradual pressure under unusually long output bursts). 2 min is aggressive enough to limit dwell time in any wedged state but cheap enough that the log volume stays manageable (≤30/h/pane, ≤150 entries/h with 5 panes — well within 5MB rotation). 1 min would log too much; 5 min reverts to roughly S25's behaviour.
- **2026-05-07 (S27) — Single bundled commit, not split across defenses.** The fixes are coupled: backgroundThrottling forces the document.hidden → hasFocus migration, the visibility handler depends on the new rlog helper for visibility-flush observability, the IPC channel is needed by the renderer logger. Splitting would create commits that don't individually pass real-use validation. Bundled is the right granularity here.
- **2026-04-27 (S26) — Recurrence on pre-S25 binary is NOT a Phase 2 escalation trigger.** Phase 2 (Canvas renderer fallback) was scoped to fire if recurrence happens *inside the 10-min flush window* — which requires the periodic flush to actually be running. A recurrence on the pre-fix binary is just the original bug doing what it always did; nothing about today's screenshot disconfirms S25's diagnosis or fix. Validation clock restarts at relaunch.
- **2026-04-27 (S26) — Diagnostic-only checkpoint, no Patton code commit.** S26's deliverable is the CLAUDE.md update (strengthened Gotcha + Session Log). The recommendation to ⌘Q + relaunch isn't a code change. Considered: forcing ⌘Q from a script — rejected, the user owns when terminal sessions die. Push of `89404e4` to GitHub remains gated on user's choice (S25 decision unchanged).
- **2026-04-27 (S25) — Periodic preventive `clearTextureAtlas()` over reactive triggers.** A `setInterval` 10-min per pane is the simplest mitigation that addresses the actual cause (gradual atlas saturation under sustained pressure), not the bursty triggers S24 hypothesised (theme swap, context loss). Cheap: `clearTextureAtlas()` is a public xterm 6 API that just clears the cache — xterm rebuilds glyphs lazily on next render, no addon disposal needed (vs S24's setCustomTheme dispose+reload path). Considered: per-prompt-redraw flush (too frequent, would stutter on heavy output bursts), per-OSC-133;D flush (too rare for non-OSC-133 sessions like Claude Code's child PTYs).
- **2026-04-27 (S25) — Auto-snapshot on `resetRenderer()`, captured BEFORE the flush.** The user invokes Reset Renderer when they SEE the bug; snapshotting before the flush captures the moment of corruption. Snapshot AFTER would only show the recovery state. Diagnostic value lives in the bug state, not the recovery state.
- **2026-04-27 (S25) — Defer Phase 2 (Canvas renderer fallback) to "if Phase 1 recurs".** Phase 2 adds dependency + settings UI + per-renderer code paths — meaningful complexity for a fallback we may not need. Phase 1 is well-targeted at the actual root cause; escalate only if 5–7 days of validation shows recurrence inside the periodic-flush window. Loose framing: pursuing root-cause-fitting changes first preserves WebGL's perf advantage for the majority case.
- **2026-04-27 (S25) — Single commit (155 LOC) instead of plan's proposed three commits.** Splitting `terminal-view.ts` across two commits would require git add -p of ~30 lines each — not worth the ceremony for a hot bug. Rollback target unchanged either way. CI auto-release threshold (patch ≤500 LOC) is well clear of the single-commit size.
- **2026-04-27 (S25) — S24 watching brief on render bug `[~] SUPERSEDED`.** The (b) garbled-glyphs question is resolved (recurred → diagnosed → fixed); the (a) double-click question carries forward as a separate Next Step. The original "watching brief" shape no longer fits — it's now a confirmed bug + fix pending validation.
- **2026-04-24 (S24) — Defensive hardening for the render-corruption bug, not reproduction-first diagnosis.** User report was a one-off screenshot, no crash, no WebGL context-loss in the log. Top hypothesis (stale atlas after theme swap) is plausible but not proven; proving it would require reproducing a bug the user can't reproduce. Instead shipped: atlas-flush on theme change (the most plausible defensive fix, near-zero cost, one-frame flicker on rare theme changes) + a user-triggered Reset Renderer command for when the state recurs + GPU breadcrumbs to catch the next occurrence with more signal. Accepts that the bug may still recur — we'd rather give the user a one-keystroke escape hatch than ship a speculative "fix" that might be wrong.
- **2026-04-24 (S24) — Unified double-click across ALL link types** (URLs + file paths + markdown), not the hybrid VS Code/iTerm convention (Cmd+click for files, single-click for URLs). User explicitly picked this to match Claude Code chat. Downside: URLs require double-click now (muscle-memory change from standard browser behavior). Upside: no stray opens while selecting text, consistent mental model across all link types, matches the tool the user spends the most time in.
- **2026-04-24 (S24) — `event.detail === 2` gate over custom `dblclick` listener.** Minimal-change path: xterm.js forwards the native MouseEvent to link-provider activate, and Chromium's `detail` is a reliable click-count. If empirically detail always resolves to 1 (xterm may collapse gestures), the fallback is a native `dblclick` listener on `terminal.element` with hit-testing against the active link range — but that's additional code we shouldn't pre-emptively write. Try the minimal path first.
- **2026-04-24 (S24) — VS Code resolved via app-bundle path before PATH lookup.** Most users who install VS Code don't run "Shell Command: Install 'code' command in PATH" inside the app. Resolving `/Applications/Visual Studio Code.app/Contents/Resources/app/bin/code` directly catches the majority case without any manual setup. Still falls through to `code` on PATH so Cursor/Codium/fork CLIs that expose a `code` shim keep working.
- **2026-04-24 (S24) — `shell.openPath` final fallback, not silent ENOENT.** Previous behavior logged ENOENT and opened nothing; 20+ silent failures accumulated in `main.log` over 4 days before being noticed. Now falls through to the macOS default-app opener (Preview.app for `.md`, etc.) so the user gets *something* even without a code editor. Loses `:line:col` — acceptable trade: "opens" beats "silently failed".
- **2026-04-24 (S24) — Reset Renderer is user-triggered (palette command), not auto-applied on suspicion.** Considered auto-calling `resetRenderer()` on some heuristic (e.g. scheduled flush every N minutes, or on detecting suspicious character sequences). Rejected: over-eager auto-flushing in the working case burns a frame for no benefit and masks the underlying signal. Making it user-triggered means we actually learn whether the recovery works the next time the bug recurs.
- **2026-04-24 (S24) — Theme swap disposes+reloads the WebGL addon synchronously, not deferred.** Considered a debounce (batch multiple rapid theme changes into one flush), but theme changes are rare (1-2 per hour at most) and a one-frame flicker per change is imperceptible. The immediate rebuild also guarantees the atlas never carries stale colors even for a single frame. KISS.

## Gotchas
- **`backgroundThrottling: false` in `webPreferences` is load-bearing** for the WebGL atlas-corruption defence (S27, 2026-05-07). With Chromium's default (true), the renderer is suspended/throttled when Patton goes background → on resume the WebGL texture state is silently stale or corrupted → user sees garbled glyphs until window-resize forces a reflow. Removing this setting will reintroduce the bug. Side effects: visibilityState reports 'visible' even when occluded (any "is app in background?" check must use `document.hasFocus()` not `document.hidden`); minor extra background CPU. The visibility-flush handler in `terminal-view.ts` is the recovery fallback — both layers exist deliberately.
- **`document.hidden` is unreliable in Patton** (S27). Because `backgroundThrottling: false` pins the Page Visibility API to 'visible' even when occluded, `document.hidden` is approximately always false in production. Use `document.hasFocus()` for "is the user looking at Patton?" gating. Already replaced in `app.ts:33` for the notification path; if you find another `document.hidden` callsite, it likely needs the same fix.
- **Renderer `console.*` calls don't reach `main.log` unless they go through `rlog()`** (S27). `src/main/logger.ts` only tees the main-process console. Any new `[RENDER]` or other diagnostic line you want in the file log MUST use `rlog()` from `src/renderer/services/renderer-logger.ts` — `console.info` alone reaches DevTools only and is invisible to packaged-app launches. This is exactly the gap that made S25's "is the periodic timer firing?" question unanswerable for ~10 days. `rlog()` keeps the DevTools console output too, so it's a strict superset of `console.*` for diagnostic purposes.
- **`[RENDERER]` prefix in `main.log` distinguishes renderer-bridged lines from native main-process lines** (S27). Lines starting `[RENDERER]` came through the IPC bridge from a renderer; everything else is native main-process. Useful when grepping — e.g. `grep '\[RENDERER\] \[RENDER\] resume atlas flush' main.log` finds visibility-triggered flushes specifically, vs `grep '\[RENDER\] snapshot saved'` (no `[RENDERER]` prefix) which is the main-process snapshot writer.
- **xterm.js WebGL atlas eviction is one of (at least) two distinct "garbled glyphs" triggers** — saturation-driven (S25 diagnosis: long Claude Code sessions emit many glyph variants, fixed-size atlas LRU-evicts slots, buffer cells aren't repointed) AND focus/refocus-driven (S27 diagnosis: Chromium suspends renderer in background, GPU state silently corrupts). Symptom signature is identical from the user side; only the trigger differs. Periodic `clearTextureAtlas()` (S25) addresses saturation, `backgroundThrottling: false` + visibility/focus flush (S27) addresses the focus path. Both are needed; don't remove either thinking the other handles all cases.
- **xterm.js WebGL atlas eviction is the recurring "garbled glyphs" trigger** (S25 root-cause). Long sessions with diverse glyph variants (coloured bullets, box-drawing, bold/italic/dim, many fg×bg combos) saturate the fixed-size atlas; LRU evictions reassign slots without repointing buffer cells, so historical scrollback shows wrong characters while recent output renders fine. Recovery as of S25: ⌘⇧K (Reset Renderer) or wait up to 10 min for the next periodic `clearTextureAtlas()`. Verify the periodic flush is firing via `[RENDER] periodic atlas flush` lines in `main.log`. If recurrence happens INSIDE the 10-min window, atlas saturation is faster than the timer — escalate to Phase 2 Canvas renderer.
- **`clearTextureAtlas()` is on Terminal, not WebglAddon** (xterm 6 typings — `node_modules/@xterm/xterm/typings/xterm.d.ts`). Public API; cheap; rebuilds atlas lazily on next render. **No addon disposal needed.** S24's `setCustomTheme()` path disposes+reloads the WebglAddon (more expensive, ~1 frame flicker) — keep that pattern only for when colors actually change. For periodic / heuristic flushes, plain `clearTextureAtlas()` is the right tool.
- **`app.getVersion()` in `main.log` returns `1.0.0` even after CI-versioned releases.** The release script tags git but doesn't bump `package.json` (per repo convention — git tags are source of truth). The `Patton main process started (vX.Y.Z, ...)` startup line is therefore meaningless for diagnosing "is the running build current?". Use the asar mtime instead: `ls -lt /Applications/Patton.app/Contents/Resources/app.asar` — that timestamp matches when `npm run package` last ran.
- **S24→S25 lesson on hypothesis ranking under unreproducible bugs.** When the user can't reproduce a bug, ranking hypotheses by "what's defensively easy to fix" rather than "what evidence supports" can chase the wrong root cause for an entire round. S24 led with theme-swap and context-loss because they were code-tractable; the actual cause was gradual atlas saturation, which the existing evidence (one-off, no crash, no logged context loss) was already pointing toward. Rule going forward: in unreproducible-bug territory, rank hypotheses by what *evidence supports*, not by *what's easy to mitigate*. Defensive fixes for the wrong cause buy nothing but session burn — and worse, they create the false belief that the bug is fixed.
- **`setCustomTheme()` is called BEFORE `mount()` on new tabs that inherit the current theme** (`tab-manager.ts:153-155`). Any WebGL-aware code in setCustomTheme must guard `if (this.webglAddon)` — otherwise it'll try to dispose/reload an addon that doesn't exist yet. The guard is in place; don't remove it when refactoring. Post-mount theme changes hit the real flush path; pre-mount just sets the theme option for the upcoming `loadWebgl()` call.
- **Garbled-glyph "atlas eviction" symptom is not always a Patton bug** (S27 reorientation, 2026-05-07). User confirmed the same character-corruption signature reproduces in **iTerm2** during the period S25/S26/S27 spent diagnosing it as a Patton/xterm.js issue. Both Patton (WebGL via ANGLE/Metal) and iTerm2 (native Metal) sit downstream of the macOS GPU + CoreText font subsystem — a system-level issue (font-cache corruption, Metal driver state, OS update) presents identically in both. Discriminator: reproduce in **Apple Terminal.app** (CoreGraphics, no Metal). Same → font/CoreText layer; only Metal-using apps → GPU layer. Triage: `sudo atsutil databases -remove` + restart resets CoreText's glyph cache. S27's defences (`backgroundThrottling: false`, visibility-flush, auto-reload) still ship as defensive value but were chasing a Patton-shape cause for a system-shape bug. Lesson reinforces #2 above: when a user can't reproduce on demand, **check whether the bug reproduces in a different terminal app** before any hypothesis about Patton internals.
- **macOS does NOT hot-swap a replaced `.app` bundle.** After `npm run package` reinstalls to `/Applications/Patton.app`, the running Patton process is still the OLD binary. ⌘Q + relaunch required to pick up new code. Detection recipe: `ls -lt /Applications/Patton.app/Contents/Resources/app.asar` (asar mtime) vs `ps -o lstart= -p $(pgrep -f Patton.app | head -1)` (process start). If process start < asar mtime, the running build is stale. S26 (2026-04-27 evening) hit this exactly. Second confirmation channel: grep `main.log` for the post-fix log signature.
- **`app.getVersion()` returns `1.0.0` even after CI-versioned releases.** Release script tags git but doesn't bump `package.json` (git tags are source of truth). The `Patton main process started (vX.Y.Z, ...)` startup line is meaningless for "is the running build current?". Use the asar mtime instead.
- **Packaged asar minifies identifier names but preserves literal values.** Verifying a shipped change: don't grep for original variable names (`event.detail !== 2` minifies to `a.detail!==2`). Grep for literal string constants (`'Reset Renderer'`, regex source strings) — those survive minification.
- **Packaged Electron apps launched from Dock/Finder route main-process stderr to `/dev/null`.** Without a file logger, every main-process signal is invisible. See `src/main/logger.ts`. Renderer console doesn't even reach that — see the rlog gotcha above.
- **`setCustomTheme()` is called BEFORE `mount()` on new tabs that inherit the current theme** (`tab-manager.ts:153-155`). Any WebGL-aware code in setCustomTheme must guard `if (this.webglAddon)` — otherwise it'll try to dispose/reload an addon that doesn't exist yet. The guard is in place; don't remove it when refactoring.
- **WebGL glyph atlas is keyed by color and can go stale on theme swap.** xterm's WebGL renderer caches glyphs keyed by `(char, bold, italic, fg_color, bg_color, ...)`. `terminal.options.theme = newTheme` mutates resolution but does NOT invalidate the cache — fix is dispose+reload the WebglAddon on every theme change. Same shape as the `minimumContrastRatio` / `onContextLoss` story.
- **xterm.js v6 registers no kitty/CSI-u handler by default.** Apps sending `\x1b[>1u` (push progressive-enhancement flags) get silently ignored — terminal keeps sending `\r` for Enter, not `\x1b[13u`. Patton's current consumers (Claude Code, fish, neovim) work fine without it.
- **OSC 133 `'prompt'` is not "awaiting input".** Fires on every prompt redraw — shell startup, session restore, SIGWINCH, `clear`, async-prompt refreshes (Starship, Powerlevel10k). Use `pane.ts fireCommandDone()` for the meaningful-transition signal.
- **Layering multiple `window.on('close')` handlers doesn't work for guards.** Electron runs every registered 'close' handler even if one calls `e.preventDefault()`. The guard must live INSIDE the destructive handler so teardown only runs when the guard passes.
- **xterm.js `attachCustomKeyEventHandler` fires for BOTH `keydown` AND `keypress`.** Returning `false` only on `keydown` still lets `keypress` through, causing xterm to send `\r`. Must return `false` for both event types.
